PostgreSQL 19 is now supported in pglayers

PostgreSQL 19 support is now available in pglayers, with 62 extension layers, ready-to-use Full and Azure profile images, and builds for both amd64 and arm64.

The images use the official postgres:19 GA image. If you want PostgreSQL 19 with pgvector, PostGIS, pg_cron, pg_textsearch, or pg_lake, you can get started without compiling extensions yourself.

A quick reminder: what is pglayers?

The official PostgreSQL Docker images provide a familiar starting point, but installing additional extensions often means adding package repositories, build tools, and compilation steps to your Dockerfile.

pglayers publishes extensions as small, composable Docker image layers. You can copy individual layers onto an official PostgreSQL image, or use a preconfigured profile that already includes the extension paths, preload libraries, and startup settings.

The idea is simple: choose your extensions without maintaining their build environments.

Try PostgreSQL 19 with extensions

The Full profile includes all 62 extensions currently available for PostgreSQL 19:

docker run -d --name pglayers-pg19 \
  -e POSTGRES_PASSWORD=change-me \
  -p 127.0.0.1:5432:5432 \
  ghcr.io/pglayers/pglayers-full:19

Once PostgreSQL is ready, connect with:

docker exec -it pglayers-pg19 psql -U postgres

For example, enable pgvector and calculate a vector distance:

CREATE EXTENSION IF NOT EXISTS vector;

SELECT '[1,2,3]'::vector <-> '[4,5,6]'::vector AS distance;

The profile takes care of the server configuration. You still create the SQL extensions you want to use in each database.

The PG19 collection includes tools for several kinds of workloads:

  • AI and search: pgvector and pg_textsearch.
  • Geospatial queries: PostGIS, pgRouting, and H3.
  • Data lake access: pg_lake.
  • Background work: pg_cron, pg_net, and pg_incremental.
  • Application development: pgmq, temporal_tables, and PLV8.
  • Data protection and observability: PostgreSQL Anonymizer, pgAudit, and pg_stat_monitor.

What is available on each PostgreSQL version?

The pglayers catalog now contains 84 extensions, but that does not mean every image contains all 84.

Availability depends on the PostgreSQL major version, upstream compatibility, published packages, and whether extensions can run together.

Why do the PG17 and PG18 Full profiles contain 83 extensions rather than 84? They include pg_duckdb and deliberately exclude the conflicting pg_lake layer. Both remain available individually. On PG19, pg_duckdb is not yet available through our build path, and the Full profile includes pg_lake.

“Full” means the broadest compatible collection for that PostgreSQL major—not a promise that every extension in the catalog can be loaded together.

The Azure profile also supports PG19

If you want a smaller collection based on extensions available in Azure Database for PostgreSQL Flexible Server, use:

docker run -d --name pglayers-azure-pg19 \
  -e POSTGRES_PASSWORD=change-me \
  ghcr.io/pglayers/pglayers-azure:19

The PG19 Azure profile currently includes 24 extensions, compared with 31 on PG17 and PG18.

Seven profile members are not yet available in pglayers for PG19:

  • age
  • documentdb
  • pg_duckdb
  • pg_failover_slots
  • rum
  • tds_fdw
  • timescaledb

The blockers differ. Some projects have PG19 compatibility changes under development or awaiting a release. Others still need compatible packages, container images, or supporting components.

DocumentDB users should stay on PG17 or PG18 for now. Although pglayers-azure:19 exists, it does not include DocumentDB or its MongoDB-compatible gateway.

As before, the Azure profile is a convenience for local development—not an exact reproduction of the managed service. Extension versions, configuration defaults, and platform-specific behavior can differ.

Compose a smaller PG19 image

You do not have to use a profile. Here is a complete Dockerfile that adds only pgvector:

FROM postgres:19

COPY --from=ghcr.io/pglayers/pgx-pgvector:19 \
    / /extensions/pgvector/

RUN echo "extension_control_path = '/extensions/pgvector/share:\$system'" \
        >> /usr/share/postgresql/postgresql.conf.sample \
    && echo "dynamic_library_path = '/extensions/pgvector/lib:\$libdir'" \
        >> /usr/share/postgresql/postgresql.conf.sample

Build and run it normally:

docker build -t my-postgres:19 .

docker run -d --name my-postgres \
  -e POSTGRES_PASSWORD=change-me \
  my-postgres:19

No extension compilation happens during this build. Docker copies the prebuilt layer.

Like PG18, PG19 uses pglayers’ isolated extension layout. Each extension lives under its own /extensions/<name>/ directory. PostgreSQL discovers its control files through extension_control_path and its modules through dynamic_library_path.

Bundled runtime libraries are kept private to each extension, avoiding file overwrites and accidental dependencies on neighboring layers. This isolation does not make inherently incompatible extensions compatible, so checking the documented conflicts still matters.

Tested beyond a successful build

An extension compiling successfully is only the first step.

The PG19 release went through checks for:

  • Self-containment: each layer resolves its runtime dependencies on the bare PostgreSQL image.
  • Cross-layer isolation: extensions do not accidentally load a sibling layer’s bundled libraries.
  • Loading and functionality: extensions load and pass their SQL integration tests.
  • Profile startup: both PG19 profiles start without warnings or errors.
  • Server health: tests detect backend and background-worker crashes.
  • Multi-architecture builds: images are built for amd64 and arm64.
  • Kubernetes integration: ImageVolume and CloudNativePG tests pass on PG19.

The GA layers and both profiles are now published. PostgreSQL 17 and 18 remain supported and tested alongside 19.

A note about upgrading

Changing an image tag from :18 to :19 is not a database migration.

Treat this as a PostgreSQL major-version upgrade: check that every extension your database uses is available on PG19, back up your data, and follow an appropriate upgrade procedure such as pg_upgrade or dump and restore.

In particular, the smaller PG19 extension set means that some existing PG17/18 workloads should wait for upstream support before moving.

Get started

You can find the current counts and examples on the pglayers website, browse the extension catalog, or read the PG19 compatibility notes.

Whether you want a preconfigured development database or a small image with a few carefully chosen extensions, PostgreSQL 19 is now another supported starting point.
